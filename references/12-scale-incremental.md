# 规模适配与增量更新

默认流程按“老朋友小群”（5–15 位核心成员、几年、几万到几十万条）设计。规模差得远时，有些模块要换写法，有些干脆不做。本文前半讲规模适配，后半讲增量更新与月报/年报。

## 一、先判断是哪一类

ingest 之后看三个数：发言人数（≥10 条的）、时间跨度、群的个数。

| 类型 | 判据 | 主要改动 |
|---|---|---|
| 两人私聊 | 只有 2 个发言人 | 年鉴改“双人年鉴”；关系弧线是主线；人物志改“双人传” |
| 小群（默认） | 3–15 位核心成员 | 按 SKILL.md 默认流程 |
| 大群 | 50–500 位发言人 | 先选核心人物（select_core.py）；事件门槛提高；人物志只写核心人物；控制成本 |
| 多群 | 主群 + 家属群/分队群 | 每群一个 key；按群定公开范围；家属只到外号 |
| 长跨度 | 10 年以上 | 分期（卷）；按期做年报；弧线按期写 |

在 config 里写 `scale` 键（`"pair" | "group" | "large"`，缺省 `"group"`），fill_prompt 会把对应门槛填进 00/01 的 `{{scale_rules}}`（pair = 本文二节“门槛降低”，large = 本文三节第 2 条，group 为空）。

## 二、两人私聊（情侣 / 挚友年鉴）

### 开工前多问一句
**成品给谁看**：只给两个人？会不会给双方家人朋友看（婚礼、纪念日）？给第三方看时，按 `family_safe: true` 的口径收紧，并额外排除：吵架与冷战的细节、前任、身体与亲密关系、对彼此家人的评价。

### 各模块怎么改

| 模块 | 是否适用 | 改法 |
|---|---|---|
| ① 导入 | 适用 | 只有一个“群”，label 写“我们”或两人的名字；members = 两人 |
| ② 大事记 | 适用，主产品 | **门槛降低**：两个人之间“一起做过的事、第一次、约定、纪念日、一句被反复提起的话”都收；单人分享对方回应了也收（群聊里“一个人说没人接”不收，私聊里每句话都有对象）。category 仍用四类：人生节点（在一起、见家长、搬家、换城市）、聚会出行（约会、旅行）、群内热议（两人反复聊的话题）、名场面（专属梗、第一次说某句话） |
| 关系弧线 | 新增主线 | 年鉴按“阶段”组织：认识 → 熟悉 → 确定关系/成为挚友 → 磨合 → 现在。阶段边界由用户确认，脚本只给数据：按月消息数、谁先开口的比例（冷场后开话题，metrics 里有）、深夜消息占比、平均回复间隔的变化 |
| ③ 小剧场 | 慎用 | 只在两人都喜欢时写；化名照旧；不写亲密情节 |
| ④ 人物志 | 改“双人传” | 一篇写两个人，不是两篇各写一人：开头一个两人同在的场景；主体是“这段关系的几个时刻”，每节写清两人当时各自怎么选；结尾的「X曰」换成两人各一段（作者自己那段是自况）。品藻改成写“这段关系”的一句话。数据卡并排两人 |
| ⑤⑥ 人物模型/盲测 | 一般不做 | 给伴侣/挚友建“可推演模型”很容易越界；用户明确要求时，只建对方的模型给用户本人看，结论标“只代表聊天里的样子” |
| 月报/年报（17/17b） | 很适合 | “我们的这个月”；纪念日前后的年报 |

### config 写法
```json
{
  "title": "我们的五年",
  "scale": "pair",
  "me": "阿杰",
  "groups": [{"key": "A", "label": "我们", "file": "exports/chat.txt", "format": "txt"}],
  "members": ["阿杰", "小雨"],
  "people": ["小雨", "阿杰"],
  "gender": {"阿杰": "男", "小雨": "女"},
  "relations": ["阿杰与小雨 2020 年认识，2021 年在一起"],
  "family_safe": true,
  "taboo_extra": ["吵架与冷战的细节", "前任", "对彼此家人的评价", "身体与亲密关系"],
  "author_title": "执笔人"
}
```

### 隐私更敏感的地方
- 私聊里的“情绪最低点”往往是最真实的，也是最不该写的。默认不收：吵架、道歉长文、某一方的焦虑和病痛、经济压力。用户要写某件，按用户的意思写。
- 截图式的原文引用风险最大——默认 `show_chat_groups: []`，页面只放事件，不放原话。
- 统计里“谁回复更快/谁先开口”可能被读成“谁更在乎”，展示前问用户要不要。

## 三、大群（50–500 人）

### 1. 先选核心人物

一般直接用 roster.py（references/01-ingest.md「多份记录与人物名单」）：它跨群合并同一人后按下面同一套指标排名、推荐核心/成员/路人，并把用户的圈定写回 config。select_core.py 是只排名、不写 config 的单群版本。
```
python3 <skill>/scripts/select_core.py --project <dir> [--top 40] [--min-msgs 30]
```
输出 `work/core.md`：每位发言人的消息数、活跃月数/跨度、被引用回复、被接话（TA 一次发言后 10 分钟内别人紧接着开口）、接话人数（多少不同的人接过 TA 的话）、被点名，以及六项百分位的综合分；末尾给出建议的 members / people 名单（JSON 片段）。

看表时注意：
- 话多但“接话人数”很少的，多半是机器人、广告号、转发号——表里会标“话多但少有人接”。
- “活跃期短”的人（只在某几个月活跃）不进 members，但他们参与的事件照样收。
- 把同一人的多个昵称并进 aliases 后重跑，否则一个人会被拆成几行、排名偏低。
- 排名给用户看，由用户圈定。大群的 members 是“统计口径”（metrics/turnmix 的列），建议 ≤30 人，否则表太宽没法读；people（写人物志的人）建议 ≤12 人。

### 2. 事件抽取门槛提高
默认规则“多人参与 / 和群里人有关 / 值得纪念都收”在大群会产出每月上百件流水账。大群改为**只收下面之一**：
- 多人参与：同一件事 **≥4 位不同发言人**参与讨论；
- 高热：当天或这一段讨论的消息数明显高于本月日均（分段文件头里“本月最热的几天”可参照）；
- 群的公共事件：群规变动、线下活动、群里成员的人生节点（官宣类）、群名/群主变更；
- 核心人物（config.people）的名场面。
不收：两三个人的闲聊、单人求助有一两人回复、广告与转发。
`config.scale = "large"` 时 fill_prompt 会把这段作为“本项目规模规则”填进 00/01 “选什么”之后的 `{{scale_rules}}`。

### 3. 分段与成本
- 大群一个月常有几万条。分段保持 `--max-chars 50000`，每个子任务给 2–4 段，读完回报行数照旧。
- 成本大头是“逐行读”。可以：
  - 先只做最近 1–2 年或用户指定的年份（`split_chunks.py --from/--to`），看效果再往前；
  - 大事记以外的模块只围绕核心人物：person_chunks 只为 people 切，证据卡、人物志、模型只做 people；
  - 抽取用便宜模型，合并/去重/年度十大用强模型；
  - 一年先做“年报”（17b）而不是逐月精修。
- 不要为了省钱改成按关键词/热度跳读——那会漏掉最热闹的短句刷屏（lessons 第 1 条）。要省就缩小时间范围，不要降低读法。

### 4. 人物志与人物模型
- 只写 people 里的核心人物；其余人在大事记里以 people 字段出现即可。
- 人物志里的“互见法”（别人怎么说 TA）在大群素材更多，但注意别人不一定是熟人——只引用 members 里的人对 TA 说的话。
- 群像总览（16）的 N×N 关系矩阵在 N>12 时改成“核心人物 × 核心人物”，其余人合并成“其他群友”一列。

## 四、多群（主群 + 家属群 / 分队群）

- 每个群一个 key，按群设公开范围（`pages.show_chat_groups`）；核心小群的原文通常不展示。
- 家属群：家属只到外号（members 可以不含家属，事件 people 里可以出现）；家属的发言不进人物模型。
- 同一件事在两个群都有讨论：抽取时各段各自抽，合并（02）时按“同一件事”合并，groups 取并集。
- 主阵地转移（例如某年起主要在家属群聊）：大事记的各年事件量会骤变，写年报和弧线时写“场合变了”，不要写成“群冷了”。
- 两个群重叠成员很多但不完全相同：metrics/turnmix 按全部群合并统计；需要分群看时，把群拆成两个项目目录分别跑。

## 五、长跨度（10 年以上）

- **分期**：按生活阶段（读书 / 工作头几年 / 成家）或按群的状态（建群 / 主阵地转移 / 重聚）分成 3–5 期，每期一个“卷”。可以在 config 里记分期（`"periods": [{"name": "大学", "from": "2012-09", "to": "2016-06"}, …]`）——**仅记录，目前没有脚本读取**：页面不会按期分栏，分期只供主控和写作子任务参考（派任务时手动写进说明）。
- **抽取**：照常按月；大事记的十大仍按年出（没有“每期十大”），每年再出一份年报（17b）。
- **人物志的弧线**：按期写变化（“大学时凌晨两点最活跃，工作后改到午休”），不要按年流水账；某一期发言骤降，写“原因看不到”。
- **人物模型**：建模员很难一次读完 10 年的证据卡。按期各出一份证据卡汇总（每期一个子任务，输入该期的 cards），建模时以“最近一期为主、早期为弧线”，并在第 9 节注明“早期的判断可能已不适用”。
- **成本**：先做最近一期和最早一期（对比最强），中间各期按需补。

## 六、增量更新

### 什么时候用
群还在聊，年鉴已经做好（有 work/stable/），隔一段时间（一个月、一个季度）重新导出一次，只为新内容补事件，已经修订过的月份不动。

### 基线
`work/incremental.json` 记着“上次整理到哪”，**按群分开记**：每个群的群名、整理到的最后一条消息时间，以及这个群每个月的消息数、首末条时间、稳定键指纹。各群分开记，几个群各自同步到不同时间点（A 群导到 10 号、B 群导到 20 号），下次 A 群补上 11–19 号的消息也只算 A 群的新增；中途新接入一个群，它在已整理月份里的消息也只当新增读，不会把整月判成 changed。旧版基线（按月、各群混在一起）会自动换算，下次 `--commit` 存成新版。第一次在已有项目上用增量时，**用做 stable/ 时的那份导出**跑一次：
```
python3 <skill>/scripts/incremental.py --project <dir> --commit
```
没有基线时脚本只推测 stable 里最晚那个月（上次导出多半截在这个月中间），并提示。

### 一轮增量的步骤
1. 把新的全量导出放到 config 里写的路径（覆盖旧文件）。
2. 对比并准备分段：
   ```
   python3 <skill>/scripts/incremental.py --project <dir>          # 先重跑 ingest，再对比
   ```
   输出一张表，每个有变化的月份归入一类（已整理的月份逐群比对，说明栏写明是哪个群、从哪条之后新增）：
   - **new**：stable 里没有的月份 → 照常切分段 `work/chunks/<月>_p<i>.txt`，按档位读：lite 走 01；standard/deep 走 00 统一阅读（事件 + 人物证据），再 collect_evidence →（多段时）02 → check_events → freeze。有 state.json 时这些分段自动出现在 pipeline 的 read 阶段，档位规则相同。freeze 只冻结新月份（已有 stable 的会跳过）。
   - **tail**：各群的旧消息都没变，只是有群多了消息（上次导出截在月中，或这个群是新接入的）→ 只把新增部分切成 `work/chunks/<月>_tail_p<i>.txt`：各群取自己上次最后一条之后的消息，新接入的群取它本月全部。抽取结果写到 `work/part_events/<月>_tail_p<i>.json`（文件头里写明了，不会覆盖 events/）；抽完跑 `incremental.py --merge-tail`：refs 换成稳定键，追加到 `stable/<月>.json` 末尾、不重排（新接入的群可能带来比旧事件更早的事件，重排会让旧下标变；页面本来就按日期排序显示）。已有事件的下标不变，所以以前的修订清单 `E:月份-序号` 和 top10.json 继续有效。和某个旧事件相隔 3 天内的新事件会被点名提示“可能是同一件事”，人工看一眼。
   - **changed**：任何一个群的旧消息变了（补导了之前漏掉的消息、导出工具换了、aliases 改了导致发言人变化）→ 整月重新切分段。重新冻结会覆盖该月的人工修订，脚本不自动删；做法是把 `stable/<月>.json` 挪到 `work/stable.bak/`，重抽重冻，再对照旧文件把修订重做一遍。
   `--dry-run` 只看表、不写文件。项目用 pipeline 编排（有 `work/state.json`）时，新月份/changed 月份的分段自动出现在 pipeline 的 read 阶段，尾部分段由 incremental 通过 `pipeline.register()` 登记成 `incremental` 阶段的 `extract:<月>_tail_p<i>`（01 抽事件）和 `merge-tail:<月>`（脚本），之后照常 `pipeline.py status / next`；没有 state.json 就照脚本打印的命令一步步跑。
   - **尾部的人物证据**：tail 分段只用 01 抽事件，不产人物证据。standard/deep 档要把新内容补进小传/模型时，另用 00 读尾部分段（`fill_prompt.py --prompt 00 --files <月>_tail_p1.txt`，卡片写到 work/cards/），再跑 `collect_evidence.py --no-events`（事件已经由 01 + --merge-tail 处理，别让它再写一遍）。
3. 构建页面：`build_chronicle.py`（以及已上线的话按 07-publish 重新部署）。
4. 收尾记基线：`incremental.py --commit`。忘了这一步，下次会把同样的月份再报一遍。
5. 可选：月报 / 年报（见下）。

### 没有消息 ID 的格式
txt / qq / 没有 id 列的 csv 的稳定键是 `L<时间戳>_<同秒序号>`。重新导出时只要旧消息原样保留，增量就正常；同一秒内补进了消息会让该月判成 changed（这是对的：旧引用可能错位）。

## 七、月报与年报

- 月报：`incremental.py --stats 2024-05` 生成 `work/digest/2024-05-stats.md`（消息数与环比、发言最多、最热的几天、凌晨条数、事件数与出镜最多，只含计数），然后
  `fill_prompt.py --prompt 17-monthly --months 2024-05` 生成说明，交给一个子任务写 `out/digest/2024-05.md`（300–600 字，轻松口吻，事实只取自 stable/，禁区同大事记）。
- 年报：`incremental.py --stats 2024` + `fill_prompt.py --prompt 17b --months 2024` → `out/digest/2024.md`（800–1500 字）。
- 月报会被发回群里：发之前让用户过一遍，可以跑隐私闸门 `privacy_gate.py --project <dir> --target digest`（out/digest/*.md；standard 档的金额、门牌住址会重点提醒）。月报的素材只来自 stable（已修订），不让子任务重读原文，避免把用户删掉的东西找回来。

## 八、配合定时任务

增量的“读”和“写”要子任务执行，所以定时任务分两段：**脚本部分可以全自动，抽取和写作部分交给 Claude 的定时任务或下次打开会话时做**。

### 每月 1 号自动准备（cron / launchd）
导出本身通常要手动（途径见 references/00-export-guide.md）；若用户的导出方式支持命令行，可以放进同一个脚本：
```bash
#!/bin/bash
# ~/bin/chronicle-monthly.sh
set -e
P=~/chronicle/my-group
SK=~/.claude/skills/chatbook
# <你的导出命令> --out "$P/exports/main.json"        # 若导出方式有命令行
python3 "$SK/scripts/incremental.py" --project "$P" > "$P/work/incremental-$(date +%Y%m).log" 2>&1
```
- cron：`0 9 1 * * /bin/bash ~/bin/chronicle-monthly.sh`
- macOS launchd：`~/Library/LaunchAgents/com.me.chronicle.plist`，`StartCalendarInterval` 设 `Day=1, Hour=9`，`ProgramArguments` 指向上面的脚本；`launchctl load` 后生效。注意 launchd 的环境里没有 shell 的 PATH，脚本里写 python3 的绝对路径。

### 抽取与写作（Claude 侧）
- **Claude Code 定时任务**（若环境有 `/schedule` 或类似的定时 agent）：每月 2 号跑一个任务，提示词写：“在 <项目目录> 按 chatbook 的增量流程：读 work/incremental-*.log 里列出的分段，用 prompts/01 抽取 → check_events → freeze / merge-tail → build_chronicle → --stats 上个月 → 用 prompts/17 写月报，写完不要 commit 基线，等我确认”。
- 没有定时 agent：用户下次打开会话说“更新年鉴”，主控读日志接着做。
- **基线 `--commit` 留给人确认后再跑**（月报看过、页面看过），不放进全自动部分：自动 commit 会把出错的一轮也记成“已完成”。

## 相关配置与命令（已接入）

- config 键：`scale`（`pair|group|large`）、`periods`（长跨度分期，可选；仅记录，目前没有脚本使用）、`lang`（references/13-english.md）；见 CONTRACT.md。
- `{{scale_rules}}`：fill_prompt 按 config.scale 填进 prompts/00、01 的“选什么”之后。
- 月报/年报模板写 `--prompt 17-monthly` / `--prompt 17b`（`--prompt 17` 不唯一，会报错并列出候选）。
