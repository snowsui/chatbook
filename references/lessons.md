# 踩坑总结（真实项目里发生过、并付出过返工代价的）

按“越早知道越省事”排序。每条：现象 → 原因 → 做法。

## 读原文

1. **事件漏了一大半。** 第一版每月限 3–8 条、允许子任务按长度/热度跳读、合并时又从 377 条删到 230 条。→ 抽取不设上限、逐行读完、合并只去重不删减（prompts/01、02）。用户最常见的反馈就是“漏了很多事”。
2. **子任务说读完了，其实只读了一半。** 有阅读员为省篇幅只读了后半段的本人发言、丢了上下文。→ 用 01 抽事件时，模板要求回报 `文件名: N 条（共 M 行，已读完）`（没读完写“读到第 X 行/共 M 行”），主控和文件实际行数对一下；用 00 统一阅读时按卡片里的 `read_to` 与 `lines` 判断（pipeline 自动查）；发现没读完就补派一个只读剩余行的子任务（输出写成 `-b` 后缀的卡片）。
3. **把别人的话安到当事人头上。** 证据卡里有大量“说话人认错”（[方括号]上下文里别人的话被当成本人的），并一路传到小传和模型。→ 证据必须带消息 id（统一阅读的卡片每条都有 id，collect_evidence 拿 id 回原文核对说话人与原话）；小传和模型的引语带 `<!--k:…-->` 出处标注，verify_citations 逐条核对。只抄原话不记出处，返工时连“这句是谁说的”都要重新全文搜。
4. **大事记读一遍、人物志又按人读一遍全量，第二遍是白花的钱。** → 统一阅读（prompts/00）一遍同时记事件和每人的证据，省掉第二遍全量阅读和对应的主控编排（references/08-pipeline.md 第 4 节有估算）。
5. **群昵称会变、多人互相起外号。** 同一个人在不同年份有 3–5 个昵称；一个外号可能被不同人用来指不同的人。→ config.aliases 归一；在说明模板里附“常见认错类型”。

## 事实与分寸

6. **性别和关系别靠推断。** “哥/嫂/大爷/姐”在熟人群里常是反串；第一版把 4 个人的性别写反，返工了上百处文案。→ 开工前就问用户，写进 config.gender/relations，所有说明模板注入。
7. **禁区要一开始就列全，而且分层。**
   - 公开页面（大事记、小剧场、人物志、数据页）：分层禁区清单以 references/09-privacy.md 第一节为准。
   - 本地私用的人物模型：可以如实写行为（粗口、八卦、荤梗、外形点评的**频率和方式**），仍不写具体隐私事实。
   - “安慰别人”的场面：写 TA 怎么安慰，不写被安慰者的具体难处。
   - 某人有不愿公开的近期私事：不仅不写，还要避免任何能让熟人对号入座的联想（换个说法、打个比方也算）。
   - **用户点名的禁区在任何模式下都生效。** 评测里抽取说明只在 family_safe=on 时注入 taboo_extra，off 模式又写着“钱、感情、健康照实记录”，结果用户点名不能写的 offer 金额（“28k”）进了公开大事记。→ taboo_extra、敏感词、真名写进“选什么”之前的硬约束；公开细节默认 standard、“照实记录”必须由用户显式选择（`public_detail` 的口径见 CONTRACT.md 与 references/09-privacy.md）。family_safe 只管恋爱暧昧、工作挫折这类分寸项。
8. **“暧昧感”是最容易踩的雷。** 两人单独吃饭、互相撩的玩笑、群友磕 CP——都不写；写了伴侣会尴尬。
9. **用户删过的东西，下游别再加回来。** 回修时子任务会“好心”把已删的素材找回来（例如外貌相关的句子）。→ 维护一份“已删除素材清单”，每次终审都检查。
   靠终审记得查不够可靠，真实项目里还是发生了两次。→ 清单交给隐私闸门检查：用户每删一句就 `privacy_gate.py --add-blocked`，构建公开页面时命中（含改了几个字的近似命中）会重点提醒，需要时可开严格模式直接拦住（references/09-privacy.md）。
   - 写真人时，发布前可以考虑让本人看看（可选的本人确认页，references/09-privacy.md 第四节）。

## 写作

10. **只看高光，人会被写成另一个人。** 证据卡挑的是名场面，模型和小传据此把每个人写得更深沉、更靠谱、更悲情；而随机抽 500 条看，所有人的日常都是接梗、哈哈哈、晒日子、吃瓜，组局只占 2–13%、关怀只占 1–6%。→ 先做日常基线（prompts/13），写作时“先日常、后高光”。
11. **框架会逼出假深度。** 要求每人都写“核心恐惧 / 错误信念”，建模员就从一句带[裂开]表情的吐槽、一道假设题的玩笑里硬挖。→ 深层判断至少 3 处彼此独立、非玩笑的证据，否则写“看不出明显的……”。
12. **反讽读成真心、替别人配的台词读成本人心声。** 典型：把“替游戏队友配的台词”当成某人的人生信条，作为全篇题眼。→ 每条引语都要看前后 5 行；终审专查“题眼”和品藻依据。
13. **同一套框架写 9 个人会写成一个人。** “嘴硬心软”“嘴上 X 手上 Y”“允许自己被照顾”在多份里几乎同句。→ 总编横向去重；“群体共性”单列，个人只写真正不同的部分；品藻放一起检查撞句式。
14. **总结段落容易千篇一律。** 9 段“史官曰”有 7 段落在“这个群没有散”。→ 明确要求每段只属于这一个人，某个意思全套最多出现一次。
15. **作者本人那篇要换写法。** 作者就是“史官”，自己评自己会别扭：改成“众人曰”（用群友这些年里对他的原话拼成），再加一段克制自嘲的“史官自况”。
    在别人那篇里，作者的人称也要事先定死，否则写作员和终审各猜各的：“史官曰”一律第一人称“我”；正文里提到作者用群昵称（第三人称），第一次出现时注明“（即史官）”（prompts/08 已写入）。

## 统计与验证

16. **按单条消息统计会把人显得过短。** 人常把一句话拆成三条发；按条数算“回一两个字占一半”，按一次发言（turn）算纯反应只有 4–13%。→ 描述说话方式一律用 turn 口径（scripts/turnmix.py）。
17. **群聊是多线并行的。** 每个人 35–48% 的发言和上文 4 条没有共同字词。只写一个“默认接法”的模型，盲测必然大面积失败。→ 模型里给“发言类型分布”和各人的“私人频道”，写戏按比例抽。
18. **12 题盲测的噪声很大（单题 ±8%）。** 逐人追分会来回过冲（这一版预测过短，下一版又过长）。→ 盲测只用来发现系统性偏差；修订建议只采纳与全量统计一致的；不追单人分数。
19. **测试题本身也会有偏。** 一版盲测题过滤了 4 字以下的回复，把模型“预测太短”的错误放大了。→ 出题脚本不过滤长度、以 turn 为单位、题目与答案分文件。
20. **大五人格分数各建模员各打各的，不可比。** → 9 人放在一起排序后再打分，口径写明（外向看冷场开题率/@人率/组局词，不看发言量）。
21. **按节拍表写群聊戏，仍然会太连贯。** 写手的本能是一个话题、人人认真接一句、最后有结论；节拍表管住了谁说、说哪类、哪里冷场，写出来的句子还是比真群聊“整齐”。另一类破绽是格式级的：引用回复的截断长度、引用回复出现的频率和真实导出不一样，评审一眼就能分出来，和人物模型像不像无关。→ 盲测按破绽归类看（references/14-creative.md）：节奏类回去收紧 18、格式类修脚本，不算模型问题。

## 工程

22. **进度只在主控脑子里、中间文件放临时目录，会话一断就丢。** 长项目一定跨会话。→ 进度放项目里的 work/state.json（pipeline.py），中间产物全放项目的 work/、out/，不放 /tmp。

23. **重新导出后引用失效。** 子任务引用的是本次运行的序号 ID。→ 抽完立刻用 freeze.py 换成稳定键。
24. **整页内嵌字体导致加载慢。** 1.4MB 的单文件页每次都要重下。→ 上线版把字体抽成带哈希的独立文件、长期缓存（package_site.py 已处理）。
25. **长页面让人翻不到。** 小剧场/人物志改成“目录 → 点开只看一篇”的单篇阅读模式（模板已内置）。
26. **登录版站点访问慢、手机打不开**，常是域名的 Cloudflare 安全级别太高 → 处理办法见 assets/site/README.md 第 4 节。

## 第一次使用时的坑（冒烟测试发现）

27. **只写一个人，就只填了一个人进名单，统计全歪。** metrics 只剩一列、turnmix 的“点名他人”漏掉对其他群友的点名。→ config 分成 members（全体，统计用）和 people（要写的人）；members 不写时脚本按发言量推断并提示。
28. **群梗隔周原样重演，抽取员各自猜怎么记。** 有的把一个月里的多次出现合成一条、refs 跨三周，有的拆开。→ prompts/01 写死「同一件事」的界定（同一场活动/连续讨论才算一件，重演的梗各自成事件并注明“又一次”），并用 check_events.py 机检 refs 数量、date、长度、跨度。
29. **数据短、只有一年时，模板里的“八年弧线”“2500 字起”会逼写作员拿复读梗凑篇幅。** → 篇幅按发言量分档、宁短勿凑；看不出变化就不硬写弧线；只有一两篇时终审走单篇模式。
30. **同一个人好几个名字、一个外号好几个人用，机器猜不准。** 群名片会改（换名后统计里成了两个人），不同群用不同昵称，txt 导出没有账号只能按名字认；反过来，“老王”“哥”这类外号在不同群、甚至同一个群里指不同的人，两个人群名片撞名也常见。→ 有平台账号的按账号自动合并；没有账号的只列“可能是同一人”的证据（引用回复指向、改名衔接、名字相近），**不自动合并**；同期都在说话的同名账号提示拆开。编号表给用户看，以用户一句话的确认为准（roster.py）。

## 数据页（统计看板）

31. **“只数不读”的页面也会泄露。** 复读句、口头禅、词云都是原话的碎片：一句“离婚吧”离开上下文就是另一回事，一个高频词能暴露谁在备孕、谁在找工作；作息类榜单（夜猫子、早鸟、活跃时段）等于公开了每个人几点睡。→ 短句只取允许展示原文的群（复用 `pages.show_chat_groups`），所有短句和词过内置敏感词表 + 本群敏感词/真名/禁区片段 + 隐私闸门，命中就丢；作息类视图、潜水榜开工前问用户（`stats.hide` / `stats.divers`），发布前让用户过目口头禅和词云（references/15-stats-dashboard.md）。
32. **榜单的门槛要按“对谁公平”来定。** 潜水榜全员倒序，上榜的是本来就只偶尔说话的家属，成了“谁不受欢迎”榜 → 只在核心成员里点最少的几位；复读按 3 人算太稀疏，降到 2 人后混进大量“两个人各自回答同一个问题”（“好的”“我也是”）→ 次数照算，展示时滤掉应答句；口头禅按次数算会被某一天的刷屏顶上来 → 要求跨 ≥3 个月。
33. **统计结果每次构建都不一样。** 会话共现对 `set(people)` 逐对计数、词云取 `Counter.most_common(100)`，并列项的先后跟着 Python 的 hash 种子走，关系图和词云在两次构建之间“自己动了”，用户以为数据变了。→ 集合先排序再数，所有排名并列时按名单顺序/字典序打破，前端布局不用随机数；测试用两个 `PYTHONHASHSEED` 跑同一份数据，要求结果逐字节相同（scripts/test_stats.sh）。
